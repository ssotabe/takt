**これは {step_iteration} 回目のパフォーマンスレビューです。**

初回は網羅的にレビューし、パフォーマンス上の問題をすべて出し切ってください。
2回目以降は、前回指摘した項目が修正されたプランに反映されたかの確認を優先してください。

{report:plan.md} の実装計画をパフォーマンス・効率性の観点でレビューしてください。
アーキテクチャのレビュー（arch-reviewが担当）やAI特有のパターン（ai_reviewが担当）はレビューしないでください。

**パフォーマンスチェックリスト（代表的なアンチパターン — 専門的判断で観点を補完してください）:**

1. **データの不要な全量変換** — DB結果やDataFrame等をdict/list等に全量コピーしていないか。ライブラリのAPIやクエリで処理すべき
2. **ライブラリが提供する操作の自前再実装** — フィルタ、集計、ソート、結合等をループで書いていないか。ライブラリのベクトル化演算・SQL集計・組み込み関数で置き換えるべき
3. **計算量の悪い探索・ループ** — O(n²)以上のネストしたループ、dict/set/indexで改善できるもの
4. **N+1問題** — ループ内でDB問い合わせやファイルI/Oを繰り返していないか。バッチ取得やJOINで一括処理すべき
5. **必要以上のデータ読み込み** — SELECT *や全量読み込みではなく、必要なカラム・行のみ取得すべき
6. **繰り返し実行時のキャッシュ欠如** — 繰り返し実行されるスクリプトで、一定コスト以上の計算結果が毎回再計算されていないか
7. **不要な中間データ構造・メモリ上の重複保持** — 大量データを別の形式にコピー・変換して保持していないか。同じデータの複数コピーをメモリに保持していないか
8. **非効率な文字列操作** — ループ内での繰り返し結合等

これらは代表的なアンチパターンの例示です。このリスト以外にもパフォーマンス上の問題があれば、専門的判断で指摘してください。

**前回指摘の追跡（必須）:**
- まず「Previous Response」から前回の open findings を抽出する
- 各 finding に `finding_id` を付け、今回の状態を `new / persists / resolved` で判定する
- `persists` と判定する場合は、未解決である根拠を必ず示す

## 判定手順

1. まず前回open findingsを抽出し、`new / persists / resolved` を仮判定する
2. {report:plan.md} を確認し、上記チェックリストに基づいてパフォーマンス問題を検出する
3. 検出した問題ごとに、ブロッキング（実測可能なパフォーマンス劣化を引き起こす）か非ブロッキング（軽微、理論的）かを分類する
4. ブロッキング問題（`new` または `persists`）が1件でもあればREJECTと判定する
